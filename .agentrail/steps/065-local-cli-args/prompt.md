Bug and feature, moved up (2026-11-09) because parity-examples' sha1.f row flips with machine speed. (1) Bug: boot.rs set_args points (argv) at the pointer array, but reva.f's argv (argv2: zcount + 1+) walks NUL-separated strings from (argv), so it must point at the first string: '0 argv type' prints the pointer's bytes (^Lp^C) today, for every index. Consequence found: examples/revafind.f saves its image as '1 argv' with no extension, a 1.48 MB file named ^Lp^C in parity's shared work folder, and sha1.f, given no files, hashes '1 argv' (clamped to 0) = that file, at about 5.75 s against the 5 s limit (it was just under before the boot words grew; recorded as timeout in local-notebook-builtin). (2) Feature (found 2026-10-30): original Reva included only argv[1] and left the rest of the command line to the program (examples/sha1.f hashes argv[2..]); reva-cli treats every positional argument as a file to include, so programs that take arguments cannot get them, and argc is 1. Add 'reva prog.f -- arg ...' (and keep 'reva a.f b.f' as it is): argv[1] the program, after -- the words become argv[2..] and argc counts them, as the original did. Beware: with argv fixed, a program that saves under an argv-derived name (revafind.f) must not write into the checkout or /reva (parity runs examples by absolute path). Document it (docs/getting-started.md, --help), a golden for argc/argv, and give parity-examples.sh a way to pass arguments to examples that need them (sha1.f with a real file), so it becomes a passing, timing-independent row.
